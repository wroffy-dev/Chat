# 13 — Database Design (PostgreSQL + Prisma)

Status: **Partly implemented.** §3.1–3.4 and §3.13 exist as migration `phase2_accounts_sessions_audit`; §3.5–3.7 as `qr_connection` (permanence enforced by a trigger rather than role grants, because a separate app role is not set up yet). §3.8–3.10 exist as migration `chat`; §3.11–3.12 as `calls`. The other tables are still proposed. This document is the source of truth for table and
column names used in the other docs.

## 1. Conventions

- PostgreSQL 16 or newer (use the version Coolify offers; **verify**). Prisma ORM with Prisma Migrate.
- Primary keys: `uuid` generated by `gen_random_uuid()` unless stated.
- All timestamps `timestamptz`, written and compared in **UTC** (`now()` on the server; client-provided
  times only where noted and validated).
- Enumerations stored as `text` with `CHECK` constraints (simpler migrations than PG enums).
- Secrets and tokens are stored only as hashes (`bytea`, SHA-256) or encrypted values.
- Two database roles:
  - `vc_migrate` — owns the schema; used only by `prisma migrate deploy` at release time.
  - `vc_app` — used by the running backend: `SELECT/INSERT/UPDATE/DELETE` as needed, **no DDL**,
    **no DELETE on `connections` and `audit_events`**.
  - Retention clean-up of `audit_events` runs in a scheduled job as `vc_maint` (DELETE on `audit_events`
    only, by age): `node dist/cli.js maint:purge-audit` with the `vc_maint` connection string (compose
    service `audit-retention`; it runs without `ADMIN_TOTP_ENC_KEY` or any app secret).
  - `vc_maint` also runs backups, so it can SELECT every table (`pg_dump` must lock `messages` even
    though it skips its rows).
  - **Implemented** as `deploy/postgres/grants.sql` (idempotent, re-run after every migration) and
    checked by `deploy/postgres/verify-roles.sh` in CI: each refused action must fail with
    "permission denied", and the backend's real flows run as `vc_app`.

## 2. Entity overview and justification

| Table | Why it exists |
|---|---|
| `users` | The two app accounts |
| `admin_accounts` | Separate admin identity ([04 §2](04-accounts-and-authentication.md#2-identity-model)) |
| `sessions` | App sessions, refresh rotation, **and device push registration** (merged: a device registration is only valid for one authenticated session, so a separate `devices` table adds nothing) |
| `admin_sessions` | Admin console sessions (different lifetime and cookie model) |
| `qr_tokens` | Single-use pairing tokens |
| `connection_requests` | Pending/accepted/rejected requests and their audit trail |
| `connections` | The permanent pair; kept immutable |
| `conversations` | Chat counters and clear epoch, separated from the immutable `connections` row |
| `conversation_participants` | Per-user read cursor and chat presence lease |
| `messages` | Message text until cleared |
| `calls` | Call state machine and minimal metadata |
| `call_diagnostics` | Quality measurements required by the test plan |
| `audit_events` | Security and admin action trail |
| `error_events` | Summarised errors for the Admin Console |
| `app_settings` | Allow-listed admin-editable settings |
| `location_shares` | **Only if D-06 is approved** |

Not created, on purpose: `devices` (merged into `sessions`), `roles` (two fixed identity types), rate-limit
tables (in-memory + `users` columns), location history (prohibited), media/attachments (prohibited),
profiles (prohibited), refresh-token table (refresh state lives on the session row).

```
users 1─┬─* sessions
        ├─* qr_tokens (owner)
        ├─* connection_requests (requester / owner)
        ├─* conversation_participants
        ├─* messages (sender)
        ├─* calls (caller / callee)
        └─0..1 location_shares
connections 1─1 conversations 1─* messages
                         └─2 conversation_participants
connections 1─* calls 1─* call_diagnostics (≤ 2 per call)
admin_accounts 1─* admin_sessions
```

### 3.1 users

|---|---|---|---|
| `id` | uuid PK | no | |

### 3.10 messages

| Column | Type | Null | Notes |
|---|---|---|---|
| `id` | uuid PK | no | |
| `conversation_id` | uuid FK | no | `ON DELETE CASCADE` |
| `seq` | bigint | no | |
| `epoch` | bigint | no | `clear_epoch` at send time |
| `sender_user_id` | uuid FK | no | |
| `client_message_id` | uuid | no | |
| `body` | text | no | `CHECK (char_length(body) BETWEEN 1 AND 4000)`. **Sensitive** |

### 3.12 call_diagnostics

`id`, `call_id` FK (`ON DELETE CASCADE`), `user_id` FK, `summary` jsonb (max 8 KB; schema-validated:
path type, RTT/jitter/loss/bitrate/resolution/FPS stats, freezes, reconnects, battery/thermal, network
changes, device model, Android version, app version), `created_at`. UNIQUE `(call_id, user_id)`.
No IP addresses, no location. Retention: same as `calls`.

### 3.14 location_shares (proposed — only if D-06 approved)

`user_id` uuid PK FK, `enabled` boolean, `consent_version` integer, `consented_at`, `precision` text,
`latitude` numeric(8,5), `longitude` numeric(8,5), `accuracy_m` real, `captured_at`, `received_at`,

nulled on disable and after 24 h. Backups exclude data. **Sensitive.**

### 3.15 app_settings

`key` text PK (allow-listed in code, [05 §5](05-admin-console.md#5-permitted-settings-app_settings)),
`value` jsonb, `updated_at`, `updated_by_admin_id`. Validated in code against a per-key schema.

### 3.16 error_events

`id` bigint PK, `first_seen_at`, `last_seen_at`, `fingerprint` text UNIQUE (route + error code),
`route`, `error_code`, `count`, `last_request_id`, `acknowledged_at`. No bodies, no stack traces (those go
only to server logs). Retention: 14 days after `last_seen_at`.

## 4. Transactions

| Operation | Isolation / locking |
|---|---|
| QR redeem | Single conditional `UPDATE … RETURNING` + insert in one transaction ([06 §4](06-qr-connection.md#4-server-logic-transactions)) |
| Accept request | `SELECT … FOR UPDATE` on the request; `ON CONFLICT DO NOTHING` on connection |
| Send message / clear chat | `SELECT … FOR UPDATE` on the conversation row |
| Refresh token rotation | `UPDATE sessions … WHERE refresh_token_hash = $1 AND revoked_at IS NULL RETURNING` (atomic compare-and-swap) |
| Start call | Insert guarded by the partial unique index; conflict → `409 CALL_IN_PROGRESS` |
| Password reset | Update hash + revoke all sessions + audit in one transaction |

Default isolation READ COMMITTED is sufficient with the explicit row locks above.

## 5. Consistency of message deletion across devices

1. The server is the only source of truth; devices hold messages in memory only.
2. Deletion is a single transaction that also increments `clear_epoch`.
3. Every send carries the client's epoch; sends from an older epoch are rejected, so nothing composed
   before a clear can be inserted after it.
4. Every history read returns the current epoch; a client with an older epoch discards its state.
5. Offline devices: on reconnect they fetch history (step 4) before showing anything.
6. Backups never contain message data, so restoring cannot resurrect messages.

## 6. Migrations and schema evolution

- Prisma Migrate; migrations committed to Git; reviewed like code.
- Release step: `prisma migrate deploy` runs as `vc_migrate` before the new backend version starts
  (Coolify pre-deployment command or container entrypoint step).
- Take a backup immediately before every migration.
- Use **expand → migrate → contract**: add new columns/tables first (backwards compatible), deploy code
  that uses them, remove old columns in a later release. This keeps rollback of the app possible without
  rolling back the schema.
- Raw SQL migrations for things Prisma does not model: partial unique indexes, `CHECK` constraints, role grants.

## 7. Backup and restore

Details in [16 §11](16-deployment-and-operations.md#11-backups-and-restore). Summary:
daily `pg_dump` (custom format) with `--exclude-table-data=messages --exclude-table-data=location_shares`,
encrypted, uploaded offsite; only the last 24 hours of backups kept (D-12); monthly restore test into a scratch database.
